# WaveForge 原文歌詞對時與字幕匯出附錄

研究日期：2026 年 10 月 5 日

## 要完成的使用流程

使用者選取音檔，貼上「一行一句」的正確歌詞，WaveForge 找出每句開始與結束的時間。使用者檢查少數不確定片段，必要時重跑或拖曳調整，最後匯出 **LRC、SRT、ASS、TXT**。

**歌詞以使用者貼上的原文為準。** 分析器負責找時間，不負責重寫、翻譯、補詞、刪詞或改標點。找不到的句子要清楚標成待確認，不能把整首歌平均切成幾段來假裝完成。

這是原功能規格 F15 的深入版本，編號使用 **L01–L12**。它可以先接在現有單檔播放器與波形上，之後再併入完整 DAW；不必等修音、鋼琴卷軸、AI 換聲或改詞重唱全部完成。

「原文完整保存」可用程式嚴格驗收；「每句時間完全正確」需要真實音訊、模型適用性與人工確認，不能承諾任意歌曲、任意語言都百分之百自動成功。

## 先分清三種工作

- **轉文字 ASR**：聽音訊，猜唱了哪些字。這裡只能幫忙找位置與發現疑點，不能取代使用者歌詞
- **強制對齊 Forced alignment**：已經知道要找哪些字，再估計各個字或音節出現的時間。提供正確文字有幫助，但文字與實際演唱不同時，演算法仍可能硬配到錯的位置
- **字幕輸出**：把已採用的文字與時間，依不同格式寫成檔案。能產生格式正確的字幕，不代表歌詞時間已經聽對

FFmpeg 負責讀取媒體、解碼、重取樣、裁切與格式處理，**不是歌詞語意對齊模型**。把 MP3 轉成 WAV，不會自然產生逐句歌詞時間。[FFmpeg 官方文件](https://ffmpeg.org/ffmpeg-all.html)

## L01 選取音檔與鎖定原文

**白話目的**：讓畫面和輸出使用你提供的歌詞，不被自動辨識偷偷改掉。

**UI 動作**：選音檔 → 貼歌詞 → 查看逐行預覽 → 按「以這份原文對時」。每行旁顯示行號，文字預設鎖定，想改詞須按「編輯原文」並產生新版本。

**資料規則**：保存收取到的完整文字、原始逐行文字、行序及穩定 lineId。相同副歌重複三次就是三個不同 lineId，不能因文字一樣而去重。空白行保留在原稿中，但不當成有聲歌詞強制對齊；「副歌」「間奏」等文字不能自行當註解刪掉，需使用者標成非演唱行。

**接受標準**：對時、二次掃描與匯出都不改 rawText；每個有聲歌詞行的文字及順序可與已確認原稿逐行核對；TXT 原文輸出保留原稿的空白、標點與換行。貼上時以程式實際收到的字串為保存基準；若匯入文字檔且要逐 byte 保存，另外保存原始 bytes 和編碼，不假裝瀏覽器貼上能還原未知的原始檔案編碼。

**初學者檢查**：按「查看原文差異」應顯示沒有文字變動；只看到時間增加。

## L02 國語 外語與混合語言

**白話目的**：同一句裡有「我 still love you」也能分開處理讀音，輸出仍是你原本貼的寫法。

**UI 動作**：選主要演唱語言，可標記某幾行或某幾個字使用另一語言；對多音字、數字、縮寫、日文漢字或特殊人名，可填「實際怎麼唱」作讀音提示。

**資料規則**：建立獨立的 alignmentText／發音表示與字元映射。繁簡轉換、大小寫、小數或數字轉讀音、去標點、分詞、羅馬拼音、Unicode 正規化只能作用於分析副本。所有 token／音素均須能回指原始行和原文範圍；零、一對多、多對一映射都要有明確表示。

**接受標準**：中文不以空格數推算字數；英文縮寫不被硬拆成與原文不同的詞；表情符號、組合字元、全形符號與 CJK 標點不能導致位置偏移。前端若用 UTF-16 索引，後端用 Unicode code point，必須明確轉換。模型不支援的語言顯示「此段需手動對時」，不靠另一語言模型硬配並標成成功。

**限制**：模型說支援中文，仍需分清普通話、粵語及其他演唱語言。跨語言輸入還需要聲學模型的音素集合、讀音字典與 G2P 同時相容；文字看起來是英文不代表歌手一定按英文發音。

## L03 音訊準備與原始時間座標

**白話目的**：分析器可以用較小的聲音副本工作，但字幕仍準確對應原音檔。

**處理流程**：讀取音訊軌、原取樣率與時間原點 → 解碼成 PCM → 依所選模型需要重取樣與選聲道 → 保留完整「分析副本到原音訊」的時間映射。

**FFmpeg 的角色**：可使用官方解碼、resample、channel-mix、trim 等能力；並非所有模型都要求 16 kHz，因此取樣率由實際模型契約決定。裁切不能用不精確的串流複製後，又假設剛好從指定 sample 開始。FFmpeg 文件說明串流複製與精確尋址的差異。[官方 seek 說明](https://ffmpeg.org/ffmpeg-all.html#Main-options)

**接受標準**：44.1／48／96 kHz 都能映射回原始時間；每次裁切紀錄真實起點與補入的前後文，回填時加一次正確 offset；更換或刪除音訊後，舊任務不能寫進新素材。前奏、靜音、encoder delay、容器非零 start time 都須納入固定的時間原點政策並測試。

**限制**：整首立體聲直接平均可能抵消反相人聲；先檢查聲道與人聲可辨識度，必要時讓使用者選聲道。可選已分離人聲作分析，但必須驗證它與原曲同起點、同時長；分離瑕疵不應被當成新的正確聲音。

## L04 第一輪尋找每句位置

**白話目的**：先找到「這一句大概在哪一段」，再找準開始和結束。

**建議流程**：

1. 讀取已鎖定歌詞，不更動文字或行序
2. 偵測可能有人聲的區段，保留低可信區域，不把 VAD 判為無聲的地方直接刪掉
3. 以可用的辨識結果、發音比對、人工錨點或段落標記建立候選句範圍
4. 按原始 lineId 順序找一致路徑，容許間奏與未對上的行，不要求每個時間都塞滿文字
5. 在有限音訊窗口內，對該句及適量前後文做強制對齊
6. 將字／音素結果映回原文，彙整成每句 start／end 和診斷資訊

**UI 動作**：主要按鈕「自動找每句時間」；若長前奏、重複副歌或混合語言造成定位不明，只請使用者點「第一句從這裡開始」或「這是第二次副歌」，不要求整首手動重做。

**接受標準**：開始時間對應第一個實際發出的語音／歌唱單位，結束時間對應最後一個單位；顯示提前量與尾端停留屬另設的字幕樣式，不能混進聲學時間。找不到 start 或 end 就保留 null／未確定，不能以全曲時長、字數或行數平均分配。

**限制**：弱音、拖長母音、rap、哭腔、氣聲、和聲及殘響會使邊界模糊。一般說話用的 VAD／aligner 可能漏掉歌聲；「有結果」並不足以判定正確。TIFA 現成模型的官方上下文限制約一分鐘，因此不能把一首數分鐘歌曲不切段直接交給它並承諾穩定。[TIFA 模型說明](https://github.com/openvpi/TIFA/releases/tag/v1.0.0)

## L05 前奏 間奏 重複句與沒有寫出的唱詞

**白話目的**：歌曲沒有唱詞的地方就空著；重複唱的地方一段一段對。

**必須處理的情況**：

- 前奏與間奏：保留原時間，不把第一句拉到 00:00，也不把長間奏壓縮掉
- 重複副歌：用出現次序和 lineId 區分，不能只以文字相等配對最近的一次
- 原稿有詞、錄音沒有唱：標記「尚未在音訊找到」，保留原文，請使用者確認
- 音訊有 ad-lib／吶喊／哼唱、原稿沒寫：標記「此處可能有未列入的演唱」，不自動新增字，不把它塞進附近一句
- 原稿少寫重複句：報告可能少了演唱次數，不能偷偷複製歌詞行
- 長拖音：一個字可持續多個音符，不按字數平均分配時間
- 合唱／對唱重疊：允許不同演唱層重疊；第一版以主唱句子為主，無法分清時列為待確認
- 括號字、段落名稱與舞台提示：只有使用者明確標成非演唱行才免對齊；原稿與 TXT 仍保存

**接受標準**：已確認的前後句不會因中間一個漏字整段順移；無詞區域不能成為高可信歌詞區；同一句多次出現的數量、ID 與原稿一致。

## L06 可解釋的品質診斷

**白話目的**：讓使用者先看最可能有問題的幾句，而不是從頭檢查每一秒。

**UI 狀態**：已人工確認、可先試聽、需要確認、找不到、模型不支援、人工指定。顯示「為什麼需要確認」，例如「有三個字沒有時間」「與前句跨過同一段」「結尾落在長間奏」。

**診斷訊號**：可比對的文字覆蓋率、未對齊 token、空／極短音素、異常長字、越界或反向時間、過多字壓在同一時間、低人聲支持區段、與相鄰錨點衝突、重複句候選差距過小、不同方案邊界分歧。

**接受標準**：模型原始 score 與產品判斷分開保存；沒有經過校準的分數不能寫成「98% 正確」。診斷不存在時要寫「未提供品質分數」，不能把成功 HTTP 回應當作高可信。歌曲特有的長母音應是提示，不可直接判錯。

**限制**：兩個模型碰巧一致仍可能一起錯；聲音能量大不一定有人聲，VAD 也不是正確邊界的裁判。高可信門檻需要同模型、同語言和同類歌唱素材的人工作標資料校準。

## L07 只重跑疑點的第二輪

**白話目的**：第一次漏掉幾句，就集中重聽那幾句，不把已經對好的地方全部洗掉。

**UI 動作**：按「再找一次有問題的句子」→ 顯示涉及的行數、時間範圍、處理方法和成本 → 完成後對照舊時間與新候選 → 採用或保留。

**候選重跑策略**：以疑點所在的前後可靠錨點限定範圍，保留足夠前後音訊與歌詞上下文；必要時增加前後各一句，或擴大半秒到數秒的音訊範圍，仍不超過模型已驗證長度。可改用已授權的另一模型、正確語言／讀音設定、原混音與分離人聲候選；這些是可選策略，不保證第二次一定更好。

**合併規則**：

1. 任務綁定音訊 hash、原文版本、目標 lineId 及發送時的時間版本
2. 只允許修改目標集合的時間候選，不輸入新歌詞行
3. 上下文句只幫辨識；除非使用者也選取它們，不能改掉其已確認時間
4. crop 的局部時間只映射一次回原曲；重跑窗口重疊時按 lineId 合併，不能直接串接兩份列表
5. 比較候選是否改善未對齊字、越界與錨點衝突；不同引擎未校準的 score 不能直接比大小
6. 候選時間互相矛盾時保留兩版或交人工確認，**不能取平均數假裝精確**
7. 採用為原子操作；文字／素材已改版、使用者拖動過時間或任務過期時，舊回覆不得覆蓋新結果

**接受標準**：第二輪前後 rawText hash、行數、行序及非目標行的時間完全一致；重跑同一批不能增加重複行。錯誤、不支援或沒有改善就維持待確認，不把「重跑完成」等同「所有問題已修好」。

## L08 波形校正與鍵盤打點

**白話目的**：即使模型聽不準，也能用幾次點擊做出正確歌詞檔。

**UI 動作**：左側逐句列表，右側波形和播放游標；點一句循環播放前後文；拖開始／結束線，或播放時按「這句開始」「這句結束」。支援慢速試聽、整組時間平移、復原／重做及標記已確認。

**文字標籤**：「早一點出現」「晚一點出現」「只重跑這一句」「保留我調的時間」。細調可用 10 毫秒或 100 毫秒步進；時間精度不代表模型有同樣準確度。

**接受標準**：拖動只改時間；慢速播放仍記錄原曲時間，不能把 0.8 倍播放經過的牆鐘時間當字幕位置；手動時間具鎖定狀態，第二輪不能覆蓋。播放位置、波形與字幕預覽使用同一時間座標，不能各自累積 timer 誤差。

**限制**：波形只能輔助找到聲音開始，不能自動分辨唱了哪個字。末音與殘響交界本來就可能有不同標註習慣，預設規則需一致，使用者能自行調整。

## L09 保留聲學時間與顯示時間

**白話目的**：唱詞的真實位置保留下來，同時可讓字幕略早顯示、晚一點消失。

**資料設計**：每句存 acousticStart／acousticEnd；顯示提前量、尾端停留與全曲 offset 另外存。最後匯出時計算 displayStart／displayEnd，不覆寫聲學資料。

**接受標準**：重設顯示偏移可回到原邊界；開始不得為負，結束不得越過已設定媒體時間範圍，超出時提供明示選項而非隱藏修補。移動音檔、裁去前奏或調整 DAW 速度後，對時資料要跟隨已知 edit map 重新映射；沒有映射時標成需重新對時，不能保留過期時間。

**重疊政策**：主唱線通常開始時間依行序非遞減；兩行顯示重疊、對唱與和聲重疊可能合理，不一律視為錯誤。反向區間、未授權跳過行序、重複 lineId 與負時間是錯誤；合理重疊需要標註並在預覽中看得見。

## L10 LRC SRT ASS TXT 匯出

四種輸出共用同一份已採用原文與時間模型，不各跑一遍辨識。

### LRC

- 第一版支援逐句標準 LRC，時間標籤採 `[mm:ss.xx]`，xx 是百分之一秒；分鐘超過 59 時不能自行歸零
- 每次出現各寫一行，不將相同副歌壓成多時間標籤，減少相容性及行對應歧義
- 基本 LRC 主要記開始時間，不能完整表達每句結束與多層重疊。長間奏可能在某些播放器繼續顯示上一句，匯出前提醒；可另提供經使用者選擇的「空白清屏事件」，不得當作新增歌詞
- 逐字 enhanced LRC 後續才提供，且只有真實逐字／音節時間可用時啟用

FFmpeg 自己的 LRC exporter 預設使用兩位小數，可作互通測試的一個實作參考，不等於所有播放器都有完全相同擴充語法。[FFmpeg LRC 原始碼](https://ffmpeg.org/doxygen/trunk/lrcenc_8c_source.html)

### SRT

- 連續 cue 編號、`HH:MM:SS,mmm --> HH:MM:SS,mmm`、原文與 cue 間空白行
- mmm 為毫秒。每個有效 cue 都需 end 大於 start；沒有 end 的行不可假填固定兩秒
- 預設一個原文行對應一個 cue。長行可在播放器視覺換行，不自動改原稿或拆成多句
- 重疊 cue 的呈現依播放器不同，匯出前警示及預覽，不能偷偷縮短真實對唱來消除重疊

SRT 格式依序號、起止時間與文字組成；其排版支援在不同應用可能不同。[美國國會圖書館 SRT 格式說明](https://www.loc.gov/preservation/digital/formats/fdd/fdd000569.shtml)

### ASS

- 使用 ASS，不混稱 SSA；先提供普通逐句字幕，含必要 Script Info、Style 與 Events
- 一句一個 Dialogue 事件，起止時間使用 `H:MM:SS.cc`；cc 是百分之一秒，字型及位置有預設值且可調
- 後續可加 karaoke：以真實字／音節時間產生 `\k`／`\kf` 等標籤；不能把一句時長平均分給每個中文字或英文詞
- 標準 karaoke duration 為百分之一秒；一句內有停頓時要保留 gap，不能把相鄰詞直接擠連。逐項四捨五入後需控制總時長誤差，避免長句累積漂移
- 程式必須避免原文被解讀成 ASS 控制碼；需要測試大括號、反斜線、逗號與換行，不能把模型／使用者文字直接當 override tags 執行

ASS 的 karaoke 標籤及特殊字元行為以 [Aegisub 官方文件](https://aegisub.org/docs/latest/ass_tags/)作實作與預覽依據。只有行級時間時可以匯出行級 ASS，不能顯示已具備逐字卡拉 OK 對時。

### TXT

- 預設為原文 TXT，不含自動辨識改寫，保留捕獲原稿的所有行與空白
- 可另選「帶時間的 TXT」，檔名與下載按鈕需區分；未對齊行保留原文並明示時間未知，不捏造數字
- TXT 不是通用的時間字幕格式；帶時間版格式應寫清楚供人閱讀，完整可回編輯資料另存專案／JSON

### 四格式共通規則

- 預設 UTF-8，必要時提供明示的 BOM／換行相容選項；編碼政策不得修改歌詞內容
- 內部使用整數微秒或同等可追溯精度，最後一次輸出才轉成毫秒／百分之一秒；處理 59.999 秒進位，不能產生秒欄 60 或負時間
- 時間量化後若 end 不大於 start，要列為格式錯誤或請使用者接受明示最小顯示長度，不能默默拉長
- 原文含該格式無法可靠表達的保留語法時，要阻擋該格式或提出明確轉義／替代方案；不能悄悄刪括號、變全形或換詞。TXT／專案原文始終保留
- 預設「完整已確認」匯出需要每個預期歌詞行都有可用時間；若使用者選「只匯出已對時部分」，列出未包含的行，並附完整原文 TXT，不讓不完整檔案冒充完整歌曲
- 輸出摘要區分「已自動產生、仍有待確認」與「使用者已確認」。未確認的候選可經明示選擇匯出，但不打上全部驗證標記

## L11 專案 保存與後端契約

### 最小資料欄位

- documentId、textVersion、sourceAudioHash、音檔時長與原始時間基準
- lineId、originalOrder、rawText、原文 character spans、是否演唱行
- languageSpans、pronunciationHints、analysisText 及回原文映射
- startUs／endUs 可為 null；source 為 model／manual／imported；manualLocked
- status、diagnosticReasons、rawModelScores、品質判斷版本
- provider、modelId、模型版本／hash、處理取樣率、cropOffset、taskId、textRevision
- 舊候選、新候選、採用紀錄與顯示 offset；文字內容不跟候選一起被覆寫

### 後端應具備的能力

- 回報目前真實可用的語言、模型、最大窗口長度、處理位置與費用；模型未就緒時回 unavailable
- 接收原文引用、目標行與上下文，不擅自重排、補詞或翻譯
- 回傳可追溯 token／音素時間、未對齊項與失敗原因，不只給一列沒有證據的平均時間
- 任務具取消、逾時、重試、進度與版本檢查；取消前已傳到第三方的音訊不能宣稱已撤回
- 每個任務的重試具 idempotency，避免重複付費與重複結果

**禁止假實作**：沒有模型或可用後端時，顯示「自動對時未啟用，可手動打點」。不能載入預先寫好的示範時間、把總時長等分、以字數比例分配、或只產生空白字幕再標完成。

## L12 驗收與測試

### 文字不變的確定性測試

每一輪分析、二次掃描、人工調時、存檔讀回及匯出解析後，都核對 lineId、原稿版本、行數、原始文字與順序。測試包含繁體／簡體、全形標點、英文縮寫、日文、阿拉伯文、混合語言、重複副歌、空白行、組合字元、表情符號及格式保留字元。

普通字幕格式不具 lineId，可用專案側的 export manifest 核對來源行與輸出 cue；不能只以歌詞字串作唯一索引。

### 對齊品質測試

以獲授權、人工標註的真實歌唱片段建立資料集，分開評估普通話、英文、其他已支援語言與句內混語；至少含清唱、伴奏、長前奏、長間奏、重複句、拖音、rap、弱人聲、缺詞、多詞與重疊人聲。

先固定標註準則：子音開始算入，結束以最後可辨識歌唱內容為準，不自動包括整段殘響。對模糊邊界可採人工容許區間，而非假設每一句有唯一 sample 級真值。

報告至少包括：可對齊行比例、待確認行比例、起／止邊界誤差的中位數與第 90 百分位、±100／250／500 毫秒內比例、錯配到另一次副歌的比例、非演唱區的假匹配數、人工修正耗時。各語言及困難類型分開報，不用大量簡單句稀釋失敗。

這些是要量測的指標，**不是已達成的準確率承諾**。格式精度 1 毫秒不代表對齊準確到 1 毫秒。正式「可自動採用」門檻需在實測前固定，測不過就縮小宣稱範圍並保留人工確認。

### 二次掃描測試

- 一句漏對後重跑，前後已確認句與所有原文不變
- 前後有相同副歌，不會跳到錯的一次
- crop 起點非整秒、分析取樣率不同，回原曲沒有固定偏移
- 兩個重跑窗口重疊，不新增重複 cue
- 任務處理時改詞、換音檔或拖時間，舊結果不能覆蓋
- 第二輪無改善，仍顯示待確認，不把低分候選平均後變成成功

### 匯出與往返測試

LRC／SRT／ASS 經獨立 parser 讀回後，核對 cue 數、內容與量化後時間；用至少一個實際相容播放器／ASS renderer 檢查顯示。TXT 與捕獲原文比較。還要測試一分鐘進位、一小時後、相同開始時間、合法重疊、空輸入、未對齊行、零長度區間、長歌與 Unicode。

合成脈衝可驗證重取樣／裁切的時間映射，不能用它證明中文歌詞對齊能力。Mock provider 可測 UI，但不能冒充模型品質測試。

## 現行技術候選與限制

### WhisperX

可用作語音辨識輔助定位，加語言專用 wav2vec2 類對齊。程式庫為 BSD-2-Clause；實際 ASR、對齊與 VAD 模型需分開查模型卡和授權。官方明示字典沒有的字元可能無法取得時間，多人重疊處理有限，對齊模型依語言選擇。

它是語音系統，不能因為支援國語 ASR 就宣稱已支援任意國語歌唱。可作基準候選，但必須測拖音、混音及混語。WhisperX 的 segment 輸入也需要合理候選時間，不能將每行歌詞在全曲時間內獨立搜尋後直接串接。

[WhisperX 官方專案與限制](https://github.com/m-bain/whisperX)

### Montreal Forced Aligner

MFA 是文字、發音字典與聲學模型的對齊工具；有單檔流程及 TextGrid／JSON／CSV 輸出。程式碼為 MIT；各聲學模型另列授權，官方目錄中的普通話與英文 MFA 模型有 CC BY 4.0 標示，仍需檢查實際選用的模型、字典與依賴。

適合有明確讀音與字典的可控流程，歌唱長母音和多語切換仍需驗證。官方文件正在區分 legacy 與新的 Hugging Face 模型工作流程，整合要固定版本與命令契約，不抄舊教程就假設永遠可用。

[MFA 對齊工作流程](https://montreal-forced-aligner.readthedocs.io/en/latest/user_guide/workflows/alignment.html) · [程式授權](https://github.com/MontrealCorpusTools/Montreal-Forced-Aligner/blob/main/LICENSE) · [聲學模型授權目錄](https://mfa-models.readthedocs.io/en/latest/acoustic/index.html)

### SOFA

SOFA 針對歌聲對齊，使用音檔、文本／讀音、G2P、字典與相符模型，可輸出音素時間和品質分數；程式碼為 MIT。模型來自個別發布或討論頁，權重授權和語言覆蓋必須逐一核查，不能把程式 MIT 擴張為所有社群模型都可商用。

可列為歌唱測試候選，尤其具合適國語字典與歌唱權重時；不能僅根據作者相對表現敘述就認定優於所有其他方案。

[SOFA 官方專案](https://github.com/qiuqiao/SOFA)

### TIFA

TIFA 支援歌聲與語音的強制對齊，包含多語 G2P、發音候選及自檢診斷。原始碼 MIT；官方 v1.0.0 現成模型列普通話、英文、日文與粵語，約 40M 參數、約一分鐘最大上下文，**模型權重為 CC BY-NC-SA 4.0**，不應直接當作已獲授權的商業產品預設後端。

其輸出的文字 tier 經過 G2P 前處理，不能取代 WaveForge 保存的 rawText。若選它做非商業研究，仍要確認實際用途符合授權；商用需另取得適用權利或使用權利清楚的自有模型。

[TIFA 官方專案](https://github.com/openvpi/TIFA) · [v1.0.0 模型規格與授權](https://github.com/openvpi/TIFA/releases/tag/v1.0.0)

### 不宜直接沿用的舊路線

- stable-ts 有將給定文字對齊音訊與局部 refine 的 API，但官方庫已於 2026 年 5 月 30 日封存，開發暫停。可作隔離比較工具，不宜成為沒有替代方案的長期唯一後端。[官方狀態與文件](https://github.com/jianfch/stable-ts)
- 舊 TorchAudio forced alignment 教程的相關 API 已在 2.8 棄用、2.9 移除；不要在現行版本安裝完成後，才發現範例不可直接使用。若需要 CTC 對齊核心，須選現行受維護實作或隔離固定版本並承擔維護責任。[PyTorch 官方警告](https://docs.pytorch.org/audio/stable/tutorials/ctc_forced_alignment_api_tutorial.html)

## 隱私 成本與部署

- **瀏覽器本機**：原文管理、波形、手動校正、格式匯出與結果驗證可先本機運作；模型推論能否搬進瀏覽器，要另外驗證可用模型格式、算子、記憶體與裝置性能，不假設 Python 模型可直接跑
- **桌面／本機服務**：可本機處理，降低音檔上傳需要；初次模型下載仍有大小、授權與硬體需求，不應偷偷開始
- **自建伺服器**：音訊與完整原文都會離開裝置；處理前須顯示目的地、保存期間與刪除機制，工作目錄和日誌不要不必要保存歌詞全文
- **可選第三方服務**：只有在真實服務、模型、語言、費率與留存政策查證後才顯示；不要放假的 provider 選單或預設公開音訊 URL
- **成本**：開源不等於零成本，CPU／GPU、模型下載、儲存、網路、維護及可能的商業授權都需估算。此研究不提供未量測的速度與價格保證
- **FFmpeg**：授權取決於編譯包含的元件，不能只看上層 wrapper；官方列 LGPL 路線及可使整體落入 GPL 的選用部分。[FFmpeg 授權說明](https://ffmpeg.org/legal.html)

## 最小可工作版本與實作順序

### 第一步 可用的手動基礎

在目前單音檔工作階段加入原文鎖定、逐句列表、波形打點／拖曳、復原與儲存，以及四格式匯出。這一版不需要模型，不應取名「自動對時完成版」。它是模型失敗時仍可完成工作的必要基礎。

**完成條件**：一首歌能手動完成每句時間、保存重開、匯出四格式；原文核對通過，字幕播放器與原曲同步。

### 第二步 真正自動對時的最小版本

選定一個**確實能運行、權利清楚、通過歌唱測試**的後端；先以已驗證的國語／英文主唱範圍提供自動句級定位。遇到不可靠重複段落可請使用者加少數錨點，再完成窗口內對齊。外語與句內混語若模型未驗證，保留原文並走手動校正，不能顯示為自動支援全部語言。

包含一輪自動對齊、疑點清單、單句或連續少數句的第二輪、採用版本、手動補救、四格式輸出。ASS 第一版為句級樣式，不要求先完成 karaoke。

**完成條件**：除 UI 和資料測試外，必須真的跑過獲授權國語、英文與至少一組宣稱支援的混語歌唱素材；提供可重現結果、人工邊界誤差和已知失敗。若沒有合法可用模型，這一步仍屬未完成，不能以示範資料或平均時間頂替。

### 第三步 擴充語言與精細對時

再依測試加入其他語言、逐字／音節時序、ASS karaoke、不同演唱層與更佳的歌唱模型。擴充宣稱以實際語言與模型驗證為準，不以「多語模型」四字概括所有外語。

### 與 DAW 的整合順序

先穩定既有音訊載入、播放時間、清除／保存與匯出基礎，再加入第一、二步歌詞模組。完整 DAW 之後只需把同一份 lineId／時間資料綁到 AudioAsset／Clip，支援裁切與 tempo map 映射。**不需要等待 AI 換音色或改詞重唱，才能做歌詞對時。**

這份附錄完成公開技術研究與產品規格；沒有下載模型、傳送使用者音訊、付費呼叫或宣稱已實作自動對齊。
